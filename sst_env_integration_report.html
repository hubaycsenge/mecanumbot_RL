Integration report

Using `sst-env` as a dog-like behavior engine for Mecanumbot.

`sst-env-main` is a Gymnasium simulation of the Strange Situation Test. It turns ethological dog-behavior scoring criteria into reward functions and trains policies that produce attachment, acceptance, and anxiety-like behavior patterns.

Recommendation

Use it as a social selector first.

Do not replace Nav2 or our execution BT. Wrap SST as a high-level decision layer that chooses among our existing robot-safe behaviors.

What It Is Code Mapping Architecture Plan Risks Verdict
What it is

An ethology-driven RL environment, not a robot controller.

The SST repo models a dog, owner, stranger, toy, and door in a 2D room. Its value for us is not low-level movement. Its value is the encoded social behavior logic and the trained policies over that logic.

Core task

Strange Situation Test

It simulates owner/stranger episodes and rewards dog-like responses such as proximity seeking, greeting, avoidance, contact, play, passive behavior, and door-oriented anxiety.

Policy

PPO-trained actions

Pretrained models exist for `attachment`, `acceptance`, `anxiety`, and `mixed`. Each predicts one of six discrete social actions from a 17-value observation vector.

Not included

No ROS or Nav2

It does not publish `/cmd_vel`, `/goal_pose`, `/mecanumbot/subject_pose`, or safety evaluation. Those still need to remain in our Mecanumbot stack.

Files that matter

The reusable knowledge is concentrated in four files.

We should treat `sst-env-main` as a reference model and source of social behavior rules before importing any dependency into ROS.

`sst_env/sst_env.py`Defines the Gymnasium `SSTEnv`, observation vector, discrete actions, reward calculation, stepping, and rendering.
`sst_env/criteria.py`Defines the ethologist scoring criteria. This is the most reusable part for our evaluator.
`sst_env/protocol.py`Defines owner and stranger schedules across 6 episodes and 4 phases each.
`sst_env/utils.py`Defines `Action`, `HumanState`, and `CriterionType` enums.
`models/*.zip`Pretrained Stable Baselines3 PPO policies for different dog-like behavior profiles.

Robot mapping

Map SST actions onto existing BT skills.

SST actions are social intents. Our behavior tree and sim stack should remain responsible for executing those intents safely through Nav2, `/cmd_vel`, gestures, LEDs, and safety checks.

`CONTACT_OWNER`Approach or face the detected subject. In our system: `ApproachSubject`, `TurnTowardSubject`, maybe low-intensity attention cue.
`CONTACT_DOOR`Lead toward the target or checkpoint. In our system: select next checkpoint, publish `/goal_pose`, monitor status.
`PLAY`Use dog-like gestures or LED/neck/gripper attention behavior. In our system: `DogBehaviourSequence` or `LEDBehaviourSequence`.
`PASSIVE`Hold position, stop, or wait for subject state to clarify. In our system: zero `/cmd_vel`, no new Nav goal.
`EXPLORE`Scan/reposition/search behavior. In our system: rotate in place, look around, or move to a safe observation point.
`CONTACT_STRANGER`In SST this means approach stranger. In Mecanumbot guide mode this is usually a risk signal: avoid, mark wrong-target, or use detector-debug to test distractor handling.
Architecture

Keep BT as execution, add SST as decision.

The safest architecture is a layered system. SST chooses the social intent; the existing BT executes it through known ROS interfaces; our sim safety evaluator checks whether the result is acceptable.

Implementation plan

Do this in phases so rollback is easy.

This keeps the integration non-destructive. Each phase can be added as a new sim-only node or config without changing the robot’s production behavior path.

01

Port SST scoring as a passive evaluator

Add a ROS node that consumes `/sim/actors`, `/mecanumbot/odom`, `/mecanumbot/subject_pose`, and current BT action state. It computes attachment/acceptance/anxiety-style scores but does not control the robot.

02

Add an SST social intent topic

Create a node that publishes an abstract intent such as `PLAY`, `PASSIVE`, `CONTACT_OWNER`, or `CONTACT_DOOR`. At first, use rule-based selection so we can debug the mapping before loading PPO.

03

Connect intent to BT leaves

Add a sim-only BT branch or adapter leaf that maps SST intent to our existing actions: gesture, wait, approach subject, lead checkpoint, or search. Keep safety evaluation external and active.

04

Try the pretrained PPO models

Only after the rule-based adapter works, load `models/mixed.zip` or the trait-specific models. The model should choose intent; it should not send `/cmd_vel` directly.

Risks

There is useful work here, but also mismatch.

The SST environment is smaller and more abstract than our robot system. The integration needs a translation layer, not direct import as-is.

Direct replacement risk

Replacing our BT with SST directly would remove Nav2 assumptions, safety checks, hardware constraints, LEDs/accessory sequencing, and ROS topic contracts. That would be high-risk and hard to debug.

Semantic mismatch

SST's `agent` is a dog. Our robot is imitating dog-like guidance behavior for a human. `owner`, `stranger`, `door`, and `toy` need careful mapping to subject, distractor, target, and attention cues.

Dependency mismatch

The repo uses Gymnasium, Pygame, Stable Baselines3, and a Python 3.13 conda environment. ROS Humble normally runs Python 3.10, so we should not blindly mix environments inside our core ROS packages.

Safe reuse path

The criteria and action vocabulary can be ported into a ROS-native adapter. That gives us the ethological structure without destabilizing the robot launch path.

Concrete first node

The first useful implementation is passive.

Before making SST control anything, build a passive evaluator node. It gives us evidence that the mapping makes sense. 

# Proposed sim-only node
sst_social_evaluator_node

Inputs:
  /sim/actors
  /mecanumbot/odom
  /mecanumbot/subject_pose
  /sim/behavior_evaluation

Outputs:
  /sim/sst_score
  /sim/sst_markers

No /cmd_vel.
No /goal_pose.
No production launch changes.

Why passive first?

It lets us compare our current Doglike/Control/LED conditions against the SST criteria. If the score trends are meaningful, then we add a selector. If not, we adjust the mapping without risking robot behavior.

Final verdict

Use SST as the social brain, not the motor brain.

The professor’s suggestion is technically reasonable if we integrate it at the right level. SST can choose dog-like social intent and score behavior. Our existing BT/Nav2/sim stack should still execute motion, gestures, topic contracts, and safety constraints.
