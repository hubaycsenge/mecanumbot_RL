What exists now

The simulation became a real test rig.

It is not just a MuJoCo viewer. It is a ROS-facing digital twin with the same topics that the rest of the robot stack expects.

Sim bridge

MuJoCo drives ROS topics

`mecanumbot_sim_io_node` runs physics, publishes `/clock`, fake OpenCR state, odom, IMU, joint states, LiDAR scans, and scenario actor truth.

Robot shell

RViz sees the robot

The URDF, meshes, robot state publisher, TF, scan, odom, and marker topics make the simulated robot inspectable like the real one.

Human world

Actors and scenarios

YAML scenarios define subject humans, distractor humans, wall panels, and moving patrol paths for controlled perception tests.

Detector path

DR-SPAAM in the loop

The real LiDAR person detector subscribes to simulated `/mecanumbot/scan` and publishes raw detections plus selected subject pose.

Safety layer

Evaluators explain failures

Detection and behavior evaluators compare perception, commands, robot pose, and ground truth to publish human-readable safety status.

Operator input

Keyboard teleop works

The teleop package publishes `/cmd_vel`, so manual driving exercises the same command stream watched by the behavior safety evaluator.

Real robot reuse

We kept the real ROS contracts.

The twin is not a separate toy interface. It swaps the hardware layer for MuJoCo, but keeps the command, perception, TF, and visualization topics that the real robot stack already uses.

Shared with the actual robot

  • /cmd_velTeleop, behavior, and navigation-style velocity commands use the same command topic.
  • mecanumbot_teleopThe keyboard teleop package publishes the same `geometry_msgs/Twist` commands.
  • mecanumbot_sensorproc_nodeThe ROS-side odom and state processing path is reused around simulated OpenCR-style state.
  • mecanumbot_lidar_detect_peopleDetector-debug mode runs the real DR-SPAAM LiDAR person detector.
  • robot_state_publisher, URDF, TF, RVizThe robot model and visualization pipeline stay the same.
  • /mecanumbot/subject_pose, /mecanumbot/odom, /mecanumbot/scanBehavior-facing topics look like normal robot topics.

Simulated or replaced

  • mecanumbot_IO_nodeThe real serial/OpenCR hardware node is replaced by `mecanumbot_sim_io_node`.
  • OpenCR and motorsPhysical motor commands and encoder feedback are replaced by MuJoCo physics and simulated state.
  • LD08 LiDAR hardwareThe real scanner is replaced by simulated `/mecanumbot/scan` from the MuJoCo world.
  • Humans and wallsReal-world people and obstacles are replaced by scenario actors defined in YAML.
  • Oracle truth modeTruth mode bypasses DR-SPAAM and publishes ground-truth `/mecanumbot/subject_pose` for stable behavior testing.
  • Hardware timing and contact detailsPhysics and wheel contact are approximate, especially sideways mecanum motion.
Bottom line

Same interface, fake hardware.

The useful design point is that behavior and perception can be tested against the same ROS topic contracts they use on the robot, while MuJoCo stands in for the base, sensors, humans, and walls.

Build story

Phases 1 through 4 are in place.

The work progressed from basic robot simulation to scenario-based perception and behavior safety checks.

01

ROS-visible MuJoCo robot

Built the simulation I/O node so the physics model behaves like the real base from ROS' point of view: `/cmd_vel` in, odom, state, scan, and TF-compatible data out.

02

Scenario actors

Added scenario YAMLs and actor runtime support so we can place humans, walls, and moving distractors in repeatable test scenes.

03

Detector evaluation

Connected simulated LiDAR to DR-SPAAM and added evaluator outputs for subject tracking, wall lock, wrong-human lock, stale detections, and high subject error.

04

Behavior safety evaluation

Added `/sim/behavior_evaluation` so motion can be judged against perception validity and ground-truth distances to humans and walls.

Data flow

The twin speaks normal ROS.

The important design choice was to keep the external interfaces familiar: teleop and behavior publish `/cmd_vel`; perception reads LaserScan; RViz reads TF, odom, robot state, and markers.

How to run it

Two commands for the stable demo.

The recommended demo path is truth twin mode. It uses oracle subject pose, so behavior and UX can be tested without DR-SPAAM noise.

Terminal 1 - truth twin and RViz
WORKSPACE=/path/to/mecanumbot
cd "$WORKSPACE"
./mecanumbot_RL/scripts/run_truth_twin.sh use_rviz:=true
Terminal 2 - keyboard teleop
cd "$WORKSPACE"
./mecanumbot_RL/scripts/run_sim_teleop.sh
Controls

Drive manually

`w/x` forward and back, `q/e` rotate, `a/d` strafe, `space` or `s` stop. Sideways motion is limited by the simplified wheel contact model.

If stale

Rebuild first

Run `./mecanumbot_RL/scripts/rebuild_sim.sh` if generated install files are missing or stale after message, launch, or package changes.

Detector mode

Use debug mode deliberately

Run `./mecanumbot_RL/scripts/run_detector_debug.sh` only when testing the real LiDAR detector path and its failure modes.

RViz debug view

What the subject, distractor, arrows, and tracks mean.

The cluttered RViz view is the perception stress test. It is designed to show when the detector confuses the real subject with a distractor human or wall, not to look like a clean demo.

Ground truth

`SUBJECT` is decided by the scenario file

The simulator knows the correct target because the YAML scenario marks one actor with `is_subject: true`. In `two_humans_wall_discrimination`, that is `subject_human`; `distractor_human` is explicitly marked false.

Actor arrows

Green and orange arrows show motion

Arrows coming from `SUBJECT` and `DISTRACTOR` are velocity markers. They show where each simulated human is moving along its patrol path. They are not used to choose the subject.

Detector lines

`D1 -> actor` shows nearest truth

Labels such as `D1 -> distractor_human 0.73m` mean a DR-SPAAM detection was transformed into map frame, then connected to the nearest visible truth actor. This is a debug association, not a command.

Human proxy

The two green leg circles create LiDAR shape

The simplified human has torso and leg geometry. MuJoCo ray-casts the simulated LiDAR against those shapes, so the detector receives human-like scan returns. We do not manually identify the subject by measuring the leg circles.

Tracked pose

`TRACK` is what perception selected

In detector-debug mode, DR-SPAAM publishes tracked detections, and the first tracked detection becomes `/mecanumbot/subject_pose`. The evaluator then checks whether that selected pose is actually close to the scenario subject.

Safety result

`safe_idle_invalid_target` is a good failure

If perception is wrong or uncertain but the robot is stopped, the behavior evaluator reports `safe_idle_invalid_target`. That means the robot is not moving toward an unreliable target.

Truth-twin mode

  • PurposeStable demo and behavior testing.
  • Subject source`/sim/subject_pose_ground_truth` is bridged directly to `/mecanumbot/subject_pose`.
  • What it provesThe robot interface, teleop, behavior logic, RViz, and safety evaluator work without detector noise.
  • LimitationIt bypasses the hard perception problem, so it does not prove DR-SPAAM can identify the right person.

Detector-debug mode

  • PurposeStress-test the real LiDAR person detector.
  • Subject sourceDR-SPAAM reads `/mecanumbot/scan`, publishes `/mecanumbot/dr_spaam/dets`, then selects `/mecanumbot/subject_pose`.
  • What it provesThe sim can expose wrong-human lock, wall lock, stale detection, and high subject error cases.
  • Expected hard caseIf the selected pose is closer to `distractor_human` than `subject_human`, the status becomes `subject_error_high` or `wrong_human_lock`.
Behavior integration

The actual leading BT now has a sim path.

We added a non-destructive adapter path: the existing behavior tree executable runs unchanged, while a sim-only Nav2/AMCL shim provides the interfaces it normally receives from the real navigation stack.

Run actual BT in truth twin
WORKSPACE=/path/to/mecanumbot
cd "$WORKSPACE"
./mecanumbot_RL/scripts/run_sim_behaviour.sh use_rviz:=true

What the shim emulates

  • /amcl_posePublished from simulated odometry in map frame.
  • /goal_poseThe real BT publishes goals here, as it does for Nav2.
  • /navigate_to_pose/_action/statusPublishes Nav2-like accepted, executing, and succeeded states.
  • /cmd_velGenerated by the shim and consumed by `mecanumbot_sim_io_node`.
  • /set_led_statusDummy success service so startup LED calls do not need LED hardware.
Non-destructive

Real robot files stay untouched.

The new pieces are sim-only: `mecanumbot_sim_nav_shim_node`, `launch_mecanumbot_sim_behaviour.launch.py`, `run_sim_behaviour.sh`, and `sim_behaviour_setting_constants.yaml`.

First goal

Validate behavior logic

This path tests attention, route selection, checkpoint goals, accessory commands, and `/sim/behavior_evaluation` before introducing full Nav2.

Later goal

Replace shim with Nav2

Once the BT works in truth mode, the shim can be swapped for real Nav2 using sim time, map-frame TF, and simulated scan input.

Evaluation

The sim reports what went wrong.

The evaluator topics turn raw motion and detector output into concise status messages. This is what makes the twin useful for debugging behavior.

/sim/detection_evaluation

  • tracking_subjectDetector pose is closest to the designated subject.
  • oracle_tracking_subjectTruth twin mode is publishing clean ground-truth subject pose.
  • false_wall_lockDetector pose is closest to a wall actor.
  • wrong_human_lockDetector pose is closest to a non-subject human.
  • subject_error_highDetector exists but is too far from the designated subject.
  • pose_memory_onlySubject pose exists, but the current raw detector frame is stale.

/sim/behavior_evaluation

  • safe_idleRobot is stopped.
  • safe_idle_invalid_targetTarget is invalid, but robot is not moving.
  • safe_following_subjectRobot is moving with a valid target and safe distances.
  • unsafe_motion_with_invalid_targetRobot is moving while perception is wrong or uncertain.
  • unsafe_motion_with_stale_detectionRobot is moving without current raw detector output.
  • unsafe_close_to_humanRobot is moving inside the human stop distance.

Limitations

Known boundaries are explicit.

The twin is useful because it makes these constraints visible instead of hiding them behind a perfect-looking demo.

Physics

Simplified wheel contact

Forward/back and rotation are the most reliable. Sideways mecanum motion is limited by the simplified MuJoCo contact setup.

Actors

Proxy humans

Human models are simplified collision and visual proxies, not articulated people with full body motion.

Perception

Hard cases can fail

Detector-debug mode uses the real DR-SPAAM path, so wrong-target and `subject_error_high` outputs are expected findings, not sim failures.
